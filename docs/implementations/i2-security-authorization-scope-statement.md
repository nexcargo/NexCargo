## 1. Governing authority and what it obliges I-2 to do

`PROMPT 0 — NEXCARGO MASTER SYSTEM_v1.3.md:161-170` fixes precedence: (1) PROMPT 0, (2) ESS-001→009, (3) MOD-001→018, (4) integration specs and approved contracts, (5) current implementation/source code. `:175`: *"A lower-level document MUST NOT silently reinterpret or override a higher-level architectural rule."* `:171-173`: if a conflict cannot be resolved by that hierarchy, **STOP and output** the human-review token (§5 does exactly that).

## 4. The eight scope items, with cited requirements

### Item 1 — RLS policy remediation and role-resolution consistency
**Requirement.** `ESS-006:187` (all tables enforce RLS), `:195` (nothing accessible without an explicit policy), `:223` (missing RLS ⇒ table treated as non-existent), `:217` (ownership predicate shape), plus `ESS-009:83/97` (every table has one owning module; Users/Roles belong to MOD-010) and the I-1 resolver rule `nexcargo-development-state.md:140`.
**Observed.** F-I2-02 (three conventions), F-I2-07 (7 deny-all tables, of which at least `audit_logs` is spec-mandated to admit an admin role), F-I2-05/06 (operational classifications authorized through the governance table).
**Remediation.** One convention only: every role predicate resolves through `effective_marketplace_role()` or `effective_user_role()`; no policy reads `auth.jwt()` or metadata; per-table adjudication of the deny-all set against its owning module's specification, with "stays closed" written down where that is the answer.

## 7. Change-management procedure (rule 11)

Per migration, never in bulk; **`supabase db push` is not used.**

1. **Scope card**: files, objects, exact statements, the cited clause that requires the change, which findings it closes, expected advisor delta.
2. **Pre-change state**: §2.2 re-snapshotted immediately before the change, plus a repository-level capture of the current definition of any object about to be altered (the last permitted observation before privileges hide it).
3. **Reverse statement** stored with the migration before it is applied — REVOKE pairs, search_path reversals, `DROP POLICY` for each added policy.
4. **Apply** one migration at a time through a scoped `apply_migration`; where no tracked row would be created, say so.
5. **Post-change verification**: advisor re-snapshot, direct call for every revocation, application-flow regression, `tsc --noEmit`.
6. **Record** each migration in the Development State register with the file's byte profile after editing.

New files continue at `042_i2_…` in the existing `NNN_slug.sql` convention.
